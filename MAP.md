## Sec 01 - The apps and what each owns
    -the account app contains the accounts.User model as well as signup, login, and logout. It also contains StaffRequiredMixin: keeping non-staff users out of the back office end and is_staff/ is_supervisor flags for role distinction.
    -the product app contains the catalog including the category, product and tag models, searching and viewing product details, and the staff screens for creating/editing products,categories, and tags. this app also contains the seed management command.
    -the orders app contains the Cart, CartItem, Order, and OrderItem models, everything regarding checkout, customer order history as well as staff order management. This app also owns the HTMX cart views, and the context processor that supplies the cart badge in the nav bar.
    -The dashboard app owns the staff analytics page, showing revenue, order count, average order value, revenue over time and top products for a chosen period.

## Sec 02 - The path of one request
    The path of one request from the browser to the rendered home page starts with the URL resolution; matching the requested page with the corresponding link in config/urls.py. After the link is successfully matched the products/views.py file runs the CatalogView. According to the CatalogView, the templates/products/catalog.html template is then rendered, displaying the home page.

## Sec 03 - A model I read
    The cart model I read used an interesting field that I had wasn't familiar with but had an idea of the field's purpose. The Cart model contains the code: user = models.OneToOneField(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name="cart",) although the field is self-explanatory I had never seen it implemented before; this links each cart to exactly one user, and vice versa. This stanza of code also contains "related_name="cart", I wasn't sure exactly was this line was declaring and after asking the agnet found out this defines the relationship between a user and their cart, naming a path from one object to the other. The agent explained that because the User model in accounts/models.py does not have a cart field, you can use the user itself to call the users cart; I learned this way a foregin key relationship can be followed from both ends with the field name (user) covering one direction and related_name covering the other.

## Sec 04 - Deleting a category
    When attempting to delete a category with products still inside, nothing happens. This is due to the line "on_delete=models.PROTECT," this defines the constraint on category deletion. This line states a category that still has products will not be deleted until the products are moved out of the category or deleted entirely. When attempting to delete a category still containing products the admin returns an error showing "cannot delete category" as well as listing the products preventing the category from being deleted.

## Sec 05 - Where the test live
    The project uses pytest with pytest-django to run the tests, the test suite is organized so tests live inside the app they are testing. 140 tests are written as plain def test_... functions without test classes. orders/services.py and dashboard/queries.py are tested directly while the views are tested through django's test client. conftest.py is a special pytest file containing fixtures which test small individual parts of the database at a time.
